# 把一个需求变成可复用的 Skill 与工作流

本章用“把收藏视频整理成学习教材”解释 Prompt、Skill、工具、MCP、Workflow 和 Agent 如何配合，再用 B08 的技术选型思路决定在哪里实现。读完可以写出一个有明确输入、输出和失败处理的 Skill，而非只给 AI 一句“帮我整理”。

## 1. 六个概念分别负责什么

假设收到一个 B 站链接，希望得到详细中文教程。

| 组件 | 在这个任务中的职责 | 具体例子 |
| --- | --- | --- |
| Prompt | 本次任务的要求 | 本次重点学习低延迟语音，解释实现步骤 |
| Skill | 可复用的方法、模板与资源 | 如何读视频、怎样写教程、如何检查内容 |
| 工具 | 真正执行一个动作 | 获取字幕、下载媒体、转写、抽帧、写文件 |
| MCP | 宿主与外部工具/资源的一种连接协议 | 将本地转写服务暴露给支持 MCP 的宿主 |
| Workflow | 按规则组织步骤与状态 | 先字幕；缺字幕才转写；完成后生成教程 |
| Agent | 根据目标和当前结果决定下一步 | 发现口播没说参数，继续读屏幕和官方文档 |

Skill 文件告诉模型该怎么工作，不会凭空赋予视频下载、语音识别或文件写入能力。比如将“使用 faster-whisper”写进 Skill，只定义了期望；宿主仍必须有可调用的转写服务。MCP 也不等于 ASR 模型，它能承载一个 ASR 工具接口。

## 2. 视频理解的输入为什么不能只有转写

口播可能说“点击这个选项”，代码、参数和菜单名在画面里。反过来，画面只有演示效果时，口播可能解释设计取舍。两者要通过时间轴对齐。

一条可用素材至少保存四种不同内容：

```text
页面元数据：标题、作者、来源链接、说明
语音文本：start/end/text，以及ASR或原生字幕的来源
视觉观察：时间点、可见代码/界面/动作、无法辨认的细节
外部补充：官方文档与实际验证，用于补足视频没有教的步骤
```

本项目 B07 就是实例：自动转写没有产生可用段落，但视频画面能看见表达配置、Studio 和 SDK。正确下一步是读画面与官方 API，从中整理实现方法。空 ASR 既不代表视频没有价值，也不能凭标题补写所谓逐字内容。

## 3. 工作流如何拆：每一步都有可检查产物

| 步骤 | 输入 | 输出 | 失败时怎么处理 |
| --- | --- | --- | --- |
| 建档 | URL | 稳定 ID、标题、平台 | 记录无法访问，不生成观看结论 |
| 取文字 | 字幕或音频 | 带时间的文本 | 没字幕转 ASR；ASR空则检查声轨与画面 |
| 读画面 | 视频与重要时间点 | 参数、操作与效果笔记 | 小字回到原尺寸帧，不凭缩略图猜 |
| 提取知识 | 文本＋画面 | 概念、步骤、参数、疑问 | 标出缺失的具体步骤 |
| 补充理解 | 项目名、缺失步骤 | 官方说明、必要背景 | 找不到就保留问题，不虚构接口 |
| 教学整合 | 上述材料 | 完整章节与应用例子 | 检查是否仍只剩宣传摘要 |
| 发布 | 教程、来源元数据 | Markdown、索引 | 保留旧稿，检查链接后更新 |

“失败处理”应使任务能够从某一阶段恢复。例如转写完成后先落盘，写教程失败时直接读取转写；不要每次都重新下载。固定输入可用稳定 ID 去重；内容或版本变化时更新对应记录。

## 4. 一个可以迁移的 Skill 正文示例

下面是教学示例。不同宿主的 Skill 包装字段可能不同，迁移时保留任务逻辑，按平台要求填写入口信息。

```markdown
# 视频与文章学习教材整理

目标：让读者不回到原视频，也能理解主要知识并开始一个最小实践。

输入：来源列表、学习方向、已有基础、可用工具、已有缓存。

执行：
1. 读取已有记录，按稳定ID去重；用户指定收藏范围时完整建档。
2. 获取正文和字幕；缺字幕且有转写工具时调用转写。
3. 结合时间点看关键画面，补录口播没有说明的参数、代码和菜单。
4. 列出视频真正提供的知识与仍缺少的步骤。
5. 对新工具读取官方使用文档，将背景解释和补充教程标为补充内容。
6. 按知识类型整合，优先解释原理，再用一个完整例子串起步骤。
7. 输出：能解决什么问题、核心机制、前提、操作、参数解释、
   输入输出示例、可开发的应用、验证方法、练习与参考答案。
8. 将来源、阅读范围和待办放在文末。保留版本与性能条件。

没有工具时：明确缺少哪项输入；使用现有正文继续整理可支持的部分。
交付前自查：读者是否知道下一步具体输入什么、会得到什么、如何验收？
```

这个 Skill 在只有文字能力的模型上也能整理**已经提供的文本**。若要自动读网页、视频和本地文件，需由 YonWORK 配置相应工具，或先由外部流程生成这些输入。

## 5. 迁移到 YonWORK：把依赖写成能力清单

不要先问“这个模型能不能学视频”，先问工作流是否能完成以下动作：访问链接、获取媒体、调用 ASR、提供图片给视觉模型或 OCR、写入知识库。模型的推理能力与平台的工具权限是两件事。

如果公司允许在本地装 faster-whisper，可以采用：本地服务接收音频任务 → 输出带时间文本 → YonWORK 调用服务或导入结果 → Qwen/DS 整理章节。关键帧可经视觉模型形成结构化描述再交给文字模型；只有 OCR 时能补文字，无法完整解释拖拽、运动或视觉效果。

一个中间结果可以长这样：

```json
{
  "source_id": "demo-video-001",
  "topic": "low-latency-tts",
  "segments": [{"start": 12.0, "end": 18.0, "text": "示例转写"}],
  "frames": [{"time": 15.0, "observation": "界面显示流式开关，已开启"}],
  "open_questions": ["采样率是否随模型变化？"]
}
```

这些字段是自定义数据约定，不是 YonWORK 已内置的 API。平台如果暂时不能调用本地服务，仍可以手动导入 JSON/Markdown，让教材生成与媒体处理分开运行。

## 6. B08 给出的技术选择方法：先考虑谁来维护

B08 全段转写讨论了“AI 一上来给 React、数据库和部署服务，但用户不会维护”的问题。可借鉴的方法是先确认目标与已有能力，再给方案，保存选择理由。

以“每周整理十几个收藏链接”为例，先问三个具体问题：需要多人同时编辑吗？必须自动抓取登录后的收藏吗？现在会维护什么环境？答案会直接改变方案。

| 需求 | 一个起步实现 | 增加复杂度的触发条件 |
| --- | --- | --- |
| 自己阅读、检索、让AI继续用 | Markdown＋Git仓库 | 明确需要多人业务权限与复杂表单 |
| 固定步骤每周跑 | 平台工作流＋持久任务记录 | 任务依赖动态规划、复杂恢复 |
| 自动读登录后的视频 | 平台工具或独立媒体处理服务 | 实际访问方式确认后再集成 |
| 展示漂亮的阅读页面 | 在现有文档上加阅读前端 | 不必同时重写存储、鉴权与采集 |

选型后记录：选什么、为什么、需要人工维护什么、哪些问题尚未解决。这样下次 AI 不会重新给你推一套完全不同的技术栈。

## 7. 练习：把一句模糊需求改成可执行任务

原需求：“每周帮我看视频，给我总结。”

参考改写：“每周输入一批收藏链接。按稳定ID去重，已有转写直接复用；先整理每条的具体知识，再按主题生成教程。教程需解释关键机制，给一个完整应用例子和验收步骤。缺少媒体访问能力时生成明确待处理任务。完成后更新Markdown索引，来源记录放文末。”

检查理解：如果一周有 20 个视频，能否一个大 Prompt 一次性处理？可以作为小规模原型，但独立处理每条、保存中间结果再按主题整合，更容易恢复失败，也便于只重做变动的材料。拆分应服务于这些实际需求，没必要一开始就设置十几个 Agent。
